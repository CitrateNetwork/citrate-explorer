# Case study: the 4K wall — an agent eval root-caused a serving misconfig, not a model

## TL;DR

The CitrateScan agent was returning empty/short answers and scoring badly. The obvious
read was "the small model is weak / a flaky narrator." The real cause was a one-line
**inference-serving misconfiguration**: the model was served with a 4,096-token context
while its fixed request overhead (system prompt + tool schemas) was already **~4,840
tokens** — so it physically could not fit a request, let alone answer one. Raising the
served context to the model's true 128K took the eval from a noisy ~49–65% to **94.2% ±
2.0**. The eval didn't find the bug, but it narrowed the search enough that one operator
aside ("I get an error around 4k tokens") cracked it.

## Anchor incident

Timeline (all 2026-06-09 unless noted):
- **Baseline (single run): 89.5%.** Looked great. Pure sampling luck.
- **After shipping a new capability: 56.5%, twice.** Read as a regression.
- Inspection: most "regressed" items had called the **right tool**; several answers were
  **empty**. Two of the failures were the *scorer* (full-address match vs `0xaceaa7…`;
  requiring the literal word "blue").
- Hardened the eval (N-run averaging, robust scoring): honest baseline **~65% ± 3.5**.
- Empty answers persisted on tool-calling queries. Tidy (wrong) theory forming: "small
  models narrate tool results poorly."
- Operator aside: *"the context window is tiny — error around ~4k tokens."*
- Measured request overhead: **system prompt ~1,515 tok + 20 tool schemas ~3,327 tok =
  ~4,840 tok fixed**, before any user input, plus a 4,096-token output reservation and 30
  turns of history. Served context: **4,096**.
- Trimmed the overhead (~4,840 → ~1,700) and, at the source on the DGX, raised
  `llama-server` from `--ctx-size 8192 --parallel 2` (= 4,096/req) to the model's
  trained max **131,072**. Result: **94.2% ± 2.0**, empty narration gone, variance
  collapsed.

## What we expected vs. what we got

- **Expected:** a model-capability problem — better prompting, a bigger model, or
  accepting "small models are flaky" as a limitation.
- **Got:** an infrastructure-budget problem. The model never had room to answer; the
  symptom (empty/variable output) perfectly mimicked a capability deficit. Every
  prompt/tool addition along the way quietly made it *worse* by eating more of a budget
  that was already negative.

## Why it happened

1. **The served context was a default, never reconciled with demand.** `--ctx-size 8192
   --parallel 2` silently means **4,096 per request** (llama.cpp splits context across
   parallel slots). Nobody had multiplied it out against the request size.
2. **Request overhead grew invisibly.** The system prompt re-listed every tool that the
   tool *schemas* already described — paying for tool docs twice — and each new tool/
   capability added more. Fixed overhead crept past the context ceiling with no alarm.
3. **The failure mode was a capability look-alike.** "Calls a tool, then emits nothing"
   reads exactly like a weak narrator, sending diagnosis toward the model.
4. **Single-run noise masked the trend.** Until we averaged, the numbers told a
   regression story instead of a "structurally cannot fit" story.

## Indicators (early warning signs)

- An answer that **calls the right tool (HTTP 200) but returns empty text**. This is the
  signature of context exhaustion after tool results are injected — not bad reasoning.
- Accuracy that **degrades as you add prompt/tool content** while tool-selection stays
  flat.
- A served-context number you cannot quote from memory, or that is a framework default.
- `n_ctx_seq < n_ctx_train` in the model server's own startup log (llama.cpp prints
  exactly this warning — ours said `4096 < 131072`, and we'd ignored it for weeks).

## Enforcement surface

The bug class — *request overhead silently exceeding served context* — is mechanically
checkable. Recommended guards (the first is the highest-value):

1. **Fixed-overhead budget test (proposed tripwire).** A unit test that estimates
   `tokens(systemPrompt) + tokens(toolSchemas) + maxOutputTokens + historyReserve` and
   asserts it stays under a configured fraction (e.g. 60%) of the **minimum supported
   served context**. This would have failed the day the overhead crossed ~2,400 tokens
   against a 4K floor — long before users hit it. The measurement already exists
   (`z.toJSONSchema` over the registry + the prompt builder); only the assertion is new.
2. **`/api/health` context-fit check.** Probe the gateway's `/props` for `n_ctx`,
   compare to the request budget, and report `degraded` when the served context can't
   hold prompt + tools + a minimal answer.
3. **Don't ignore the server's own warning.** Surface `n_ctx_seq < n_ctx_train` from the
   model-server log into ops alerting; the tool told us for weeks.

Standing config record: the served context + how to change it now lives in memory
(`reference-dgx-llama-context`) so it can't silently revert to a default.

## What this does NOT cover

- It is not a claim that context size fixes quality in general — beyond fitting the
  request, more context mostly adds latency, not accuracy.
- It does not address genuine small-model reasoning limits (the LoRA track, RA-8,
  targets those separately).
- The fixed-overhead tripwire (#1) is **proposed, not yet implemented** — a good
  follow-up for the tripwire-author.
